# Research notes: weather

Collected and fact-checked against primary sources on 2026-10-07: the recommendation (REC), pitfalls, and a verifier's corrections and additions (NON-CONFIRMED / MISSED). Prefer these over memory, and re-check anything that looks outdated.

```text
KEY weather
REC: 1) Add a server-side weather proxy in Node: GET /api/weather?lat=..&lon=.. (or push the result over Socket.IO presence). It calls https://api.open-meteo.com/v1/forecast?latitude={lat1}&longitude={lon1}&current=temperature_2m,weather_code,is_day,cloud_cover,precipitation,rain,snowfall,wind_speed_10m,wind_direction_10m,visibility&timezone=auto&timeformat=unixtime. That is 10 variables or fewer, so each request counts as 1 API call. Use plain fetch with no SDK and AbortSignal.timeout(5000). Leave `daily` out: daily variables need a timezone and add call weight. 2) Round coordinates before caching and before they leave the client: 1 decimal (about 11 km) for the cache key, and never store raw GPS. Open-Meteo keeps request coordinates in its logs for 90 days, and MET Norway recommends a proxy so users' IPs are not exposed. 3) Cache in memory, in a Map keyed by the rounded cell. TTL is 15 minutes, matching `current.interval` = 900 s, plus 1–4 minutes of random jitter. Collapse concurrent requests for the same cell into one in-flight promise. Fetch only for cells with an online user. Serve stale data for up to 3 h on errors. On HTTP 429, back off for 1 h. Keep a daily counter that stops at about 8,000 calls, because the free tier allows <10,000/day, 5,000/h, 600/min and 300,000/month. The client re-asks every 15 min, or the server pushes when the cell refreshes. 4) Make the provider configurable. The free Open-Meteo API is for non-commercial use only. Add these settings: WEATHER_PROVIDER=open-meteo|metno|off (default open-meteo). OPEN_METEO_API_KEY: if set, switch the host to https://customer-api.open-meteo.com/v1/forecast and append &apikey=KEY; the Standard plan is 1M calls/month and reportedly $29/month, so confirm on the pricing page. OPEN_METEO_BASE_URL for a self-hosted AGPL Open-Meteo. METNO_USER_AGENT (e.g. "workchop/1.0 ops@yourdomain"), required if WEATHER_PROVIDER=metno, which calls https://api.met.no/weatherapi/locationforecast/2.0/compact?lat=..&lon=..; MET Norway data is CC BY 4.0/NLOD and can be used commercially. For MET, truncate coordinates to 4 decimals or fewer, honour Expires/If-Modified-Since, and map timeseries[0].data.next_1_hours.summary.symbol_code. Add OPEN_METEO_API_KEY and METNO_USER_AGENT to the Worker's PASSED_TO_SERVER list and to docker-compose. 5) Location, in priority order. (a) A manual city the user picks via https://geocoding-api.open-meteo.com/v1/search?name=..&count=5&language=en, proxied server-side; store name, rounded lat/lon and timezone on the user profile. (b) An opt-in "Use my location" button, never on page load, calling navigator.geolocation.getCurrentPosition with {enableHighAccuracy:false, maximumAge:3600000, timeout:10000}. It needs HTTPS (Caddy/Cloudflare) or localhost. (c) IP-based geo, used only when the operator enables it. On Cloudflare Containers, the top-level Worker fetch first deletes any client-sent x-workchop-geo-* headers. It then copies request.cf.latitude, longitude, city (encodeURIComponent'd), regionCode, country and timezone into x-workchop-geo-lat/-lon/-city/-region/-country/-tz on new Request(request,{headers}). The Worker also passes env GEO_HEADERS=workchop to the container, the same way it already sets CLIENT_IP_HEADER. These cf fields are listed under "All plans have access to". For Docker Compose behind a Cloudflare Tunnel, the operator can turn on the "Add visitor location headers" Managed Transform and set GEO_HEADERS=cloudflare to read cf-iplatitude, cf-iplongitude, cf-ipcity and cf-timezone. Plain Docker+Caddy has no IP geo: use (a)/(b). Optionally use a DB-IP City Lite .mmdb read with maxmind@5.0.7 (CC BY 4.0; needs an "IP Geolocation by DB-IP" link). (d) Otherwise no weather: show a neutral sky. 6) Reverse geocoding (coordinates to a city label): Open-Meteo has none. Use cf.city when available. Or call BigDataCloud's free https://api.bigdatacloud.net/data/reverse-geocode-client?latitude=..&longitude=..&localityLanguage=en from the BROWSER only, right after geolocation. Calling it from the server breaks its fair-use rule and gets the server IP banned. Or simply label it "Your location". 7) Map weather to the scene. WMO weather_code: 0–1 clear, 2 partly cloudy, 3 overcast, 45/48 fog, 51–57 drizzle (56/57 freezing), 61–67 rain (66/67 freezing), 71–77 snow (77 grains), 80–82 rain showers, 85–86 snow showers, 95–99 thunder (96/99 hail). Drive density from cloud_cover, rain/snow intensity from precipitation/snowfall, particle slant from wind_speed_10m/wind_direction_10m, and fog from visibility under 1000 m. Use is_day for day/night. For a smooth sun, compute the sun's position on the client with three's bundled examples/jsm/objects/Sky.js plus suncalc@2.0.2 or 1.9.0, where getPosition units differ between majors. 8) Attribution: when Open-Meteo data is shown, show the link <a href="https://open-meteo.com/">Weather data by Open-Meteo.com</a> right next to it, e.g. in the weather HUD/tooltip and the About page. Show "Data from MET Norway" when that provider is used, and the DB-IP link if the mmdb is used.
PITFALLS:
 - Licensing: the free Open-Meteo API is non-commercial only. If Workchop is sold as SaaS, has subscriptions or ads, or a business runs it as part of a product, the operator needs OPEN_METEO_API_KEY (customer-api.open-meteo.com) or must switch to MET Norway. Put this in the README and the env docs.
 - A server proxy sends every user's weather requests from one egress IP, and the free limits (10k/day, 5k/h, 600/min, 300k/month) and IP blocking apply to that IP. On Cloudflare Containers the egress IP may be shared with other tenants (not documented), which could trigger 429s for reasons outside Workchop's control. Cache aggressively, collapse duplicate requests, keep a daily budget counter, and back off for an hour on 429.
 - Keep `current` to 10 variables or fewer. Adding daily sunrise/sunset or more variables raises the fractional call weight.
 - Timezone: the default is GMT. Use timezone=auto for local time. With timeformat=unixtime, timestamps are GMT+0. With iso8601 and a timezone, timestamps are local time without an offset, so parse them with utc_offset_seconds.
 - WMO code table mismatch: the website lists 97 and calls 96/99 hail, while the server enum has 95/96/99 only. Map the whole 95–99 range to thunder and fall back to 'cloudy' for unknown codes.
 - Spoofing: any client can send x-workchop-geo-* or cf-ip* headers. The Worker must delete incoming copies before setting its own, and the Node server should trust geo headers only when GEO_HEADERS is set by the deployment, the same way CLIENT_IP_HEADER works today.
 - City names in request.cf can be non-ASCII. URL-encode them before putting them in headers. Cloudflare's managed transform sends them as UTF-8.
 - request.cf is missing in the Workers Playground and dashboard preview. Code must handle cf being undefined, and wrangler dev may return placeholder geo.
 - IP geolocation is coarse (city centroid) and wrong for VPN or corporate-proxy users. Always let the user override with a manual city or browser geolocation, and show which source is in use.
 - Browser geolocation needs HTTPS (or localhost), shows a permission prompt, and may be blocked by Permissions-Policy in iframes. Ask only after a user gesture, never on page load. With the default timeout:Infinity it can hang, so set timeout.
 - Do not call BigDataCloud's reverse-geocode-client from the server, and do not call it with stored coordinates: this gets the server IP banned. Call it only from the browser, right after geolocation.
 - MET Norway returns 403 with a generic or missing User-Agent or with coordinates of 5 or more decimals. It requires honouring Expires/If-Modified-Since, and the 20 req/s cap is per application.
 - Attribution is a licence requirement, not optional: put a visible 'Weather data by Open-Meteo.com' link next to the weather display, not only on an About page. CC BY 4.0 also asks you to indicate changes (e.g. 'conditions simplified').
 - The dbip-city-lite npm mirror's package.json says CC-BY-NC-SA-4.0 while its README says CC BY 4.0. Download from db-ip.com directly if you use it.
 - suncalc changed units between majors (1.x radians, 2.x degrees). Pin an exact version that is at least 2 weeks old (2.0.2 from 2026-09-02, or 1.9.0). 2.1.0 and 2.1.1 are under 2 weeks old as of 2026-10-07.
 - Privacy and GDPR: user location is personal data. Store only the rounded cell (about 11 km) and a city label. Do not broadcast precise coordinates to other office members; broadcast only the weather state, e.g. {code, isDay, tempC, city?}, and let users hide the city.
NON-CONFIRMED:
MISSED:
 - Free-tier concurrency limit (from Open-Meteo's server source): the free API allows CONCURRENCY_LIMIT=1 concurrent request per caller IP and queues the rest. Above CONCURRENCY_LIMIT_HARD=5 it returns HTTP 429 "Too many concurrent requests". Deduplicating per cell is not enough: the proxy needs a global limit of 1–2 in-flight upstream requests. Alternatively, batch several cells into one request with comma-separated latitude/longitude, but each location still costs at least 1 call. Sources: https://github.com/open-meteo/open-meteo/blob/main/Sources/App/Helper/Vapor/RateLimiter.swift and .../ConcurrencyGroupLimiter.swift.
 - Handling 429s (correction to 'back off for 1 h'): the 429 body is JSON {"error":true,"reason":...}. The reason is one of "Minutely API request limit exceeded...", "Hourly..." or "Daily API request limit exceeded. Please try again tomorrow." Counters reset at the next UTC minute, hour or midnight. Back off until the matching UTC boundary, and reset the app's ~8,000/day counter at 00:00 UTC rather than local midnight. Failed requests also count as 1 call, so never retry in a tight loop. Bad parameters return HTTP 400; an overloaded server returns 503.
 - Exact call weight from the source (ForecastApiResult.calculateQueryWeight): weight = max(1, max(v/10, v/10*days/14)) per location. v = (current + hourly + minutely_15 + daily variables) × number of models. The proposed 10 `current` variables give exactly 1.0. Any 11th variable, or a second `models=` entry, makes it 1.1, so keep the list at ≤10 and don't pass multiple models. Multi-location requests sum the weight of each location.
 - Open-Meteo rate-limits by source IP, so every Workchop deployment shares one budget per egress IP. Open-Meteo special-cases Cloudflare IP ranges (it uses the CF-Worker header as the slot). I could not verify whether Cloudflare Containers egress uses shared IPs (nothing in the cloudflare-docs containers pages). If it does, the free quota could be shared with other tenants. Keep the daily budget conservative there and recommend an API key. Confidence: low.
 - The commercial geocoding host is customer-geocoding-api.open-meteo.com (open-meteo-website src/routes/en/docs/geocoding-api/+page.svelte). The geocoding proxy must switch hosts as well when OPEN_METEO_API_KEY is set, and show "Location data based on GeoNames". The pricing table includes the Geocoding API in every paid tier. The key can be sent as an `X-Api-Key` header instead of `&apikey=`.
 - Cloudflare 'Add visitor location headers' Managed Transform (cloudflare-docs rules/transform/managed-transforms/reference.mdx): the header names cf-ipcity, cf-iplatitude, cf-iplongitude, cf-timezone (plus cf-ipcountry, cf-region, cf-region-code, cf-postal-code, cf-metro-code, cf-ipcontinent) are confirmed. The docs give no plan restriction for this transform. "Cloudflare always converts non-ASCII characters to UTF-8 in HTTP request and response header values": Node may parse header values as latin1, so cf-ipcity can arrive garbled. Re-decode with Buffer.from(v,'latin1').toString('utf8'); confidence medium. Treat GEO_HEADERS=cloudflare like CLIENT_IP_HEADER: enable it only when every request goes through Cloudflare, because otherwise the headers can be spoofed.
 - MDN (mdn/content geolocation/getcurrentposition): getCurrentPosition needs a secure context, "may be blocked by the geolocation Permissions-Policy", and prompts the user. The defaults are maximumAge 0, timeout Infinity and enableHighAccuracy false, so the proposed options are valid. The repo sets no Permissions-Policy or CSP today (Caddyfile and server checked). Keep it that way, or allow geolocation=(self) and connect-src for api.bigdatacloud.net if CSP is added later.
 - suncalc (npm registry): latest is 2.1.1, published 2026-10-05. Pin 2.0.2 (2026-09-02) or 1.9.0. The difference between majors is confirmed. 2.x getPosition returns `altitude` "apparent (refraction-corrected)... in degrees" and `azimuth` "in degrees, clockwise from north". 1.9.0 returns radians, with azimuth "measured from south to west". 2.x is ESM ("type":"module") with a CJS fallback and bundled index.d.ts.
 - three Sky.js exists in the repo's installed three 0.186.1, but "can only be used with WebGLRenderer. When using WebGPURenderer, use SkyMesh". The client already uses @react-three/fiber 9 and @react-three/drei 10.7.9, which ship <Sky>, <Cloud>, <Stars> and <Sparkles>. Reuse those instead of importing the addon directly. Today client/src/world/Environment.tsx uses a fixed sky colour and a fixed directional light.
 - MET Norway primary docs (api.met.no, docs.api.met.no) are blocked by the sandbox proxy, so the MET items are unverified (low confidence). Search summaries of the official ToS/FAQ say: an identifying User-Agent with app/domain and contact is mandatory, and generic UAs are throttled or blocked. They say "never use more than 4 decimals", phrased as rounding, not truncating, and that such requests will return 400 "in the immediate future". Honour Expires and use If-Modified-Since with the previous Last-Modified (304 replies). Deprecated or beta products return 203. Add random jitter to request times. The CC BY 4.0/NLOD claim and 'MET recommends a proxy to hide user IPs' were not verified. Open-Meteo's licence page lists MET Norway data as CC-BY.
 - The privacy facts in the recommendation are confirmed by the terms page. Free API: "webserver log files that may contain sensitive information such as geographical coordinates... All log files will be deleted after a period of 90 days." Paid API: "we gather certain information, including IP addresses and URLs... after a period of 90 days, all individual log files will be removed". Rounding to 0.1° before the upstream call is therefore justified for both tiers. Storing a city or rounded location on the user profile is still personal data. Showing another member's location or weather should be opt-in.
```
