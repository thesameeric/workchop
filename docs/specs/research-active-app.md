# Research notes: active-app detection

Collected and fact-checked against primary sources on 2026-10-07: the recommendation (REC), pitfalls, and a verifier's corrections and additions (NON-CONFIRMED / MISSED). Prefer these over memory, and re-check anything that looks outdated.

```text
KEY active-app
REC: 1) A web page cannot do this. The only standard signals are the page's own visibility/focus and, in Chromium only, IdleDetector (user idle and screen locked). None of them says which other app is in front. So build an opt-in "Workchop Presence Helper". Make it one zero-dependency ESM Node 22 script (workchop-presence.mjs) that uses only node:child_process.execFile and the built-in fetch. Every 5 s it reads only the frontmost app's identifier (never window titles) and maps it locally to an allowlist id. It POSTs only when the value changes, plus a 15 s heartbeat. Later it can be packaged per OS with Node SEA, which is still "Stability: 1.1 - Active development".
2) macOS: spawn a fresh `osascript -l JavaScript -e 'ObjC.import("AppKit");var a=$.NSWorkspace.sharedWorkspace.frontmostApplication;JSON.stringify({id:ObjC.unwrap(a.bundleIdentifier)||"",name:ObjC.unwrap(a.localizedName)||""})'` on every poll. A fresh process matters because NSWorkspace values only update while a run loop runs. This sends no Apple Events, so it needs no Automation, Accessibility or Screen Recording grant. It is the same NSWorkspace route Tandem documents. Match on bundle id (com.figma.Desktop, com.microsoft.VSCode, com.tinyspeck.slackmacgap, …). Do NOT use `tell application "System Events" to get name of first application process whose frontmost is true`. It triggers the Automation consent ("<Terminal/osascript> wants access to control System Events"), and it has a known bug where several Electron apps all report the process name "Electron".
3) Windows: start ONE long-lived `powershell.exe -NoProfile -NonInteractive -EncodedCommand <UTF-16LE base64>` with Node `{windowsHide:true}`. The script runs Add-Type for user32 GetForegroundWindow and GetWindowThreadProcessId once. Then it loops forever: `$h=[W.U]::GetForegroundWindow(); $p=0; [void][W.U]::GetWindowThreadProcessId($h,[ref]$p); [Console]::Out.WriteLine((Get-Process -Id $p -EA 0).ProcessName); [Console]::Out.Flush(); Start-Sleep 5`. Node reads stdout line by line. Inline/encoded commands are allowed even under the default Restricted execution policy, which only blocks .ps1 files. If `$ExecutionContext.SessionState.LanguageMode` is not FullLanguage (AppLocker/WDAC), Add-Type of Win32 APIs is blocked, so report "unsupported". Treat a 0 handle as null and ApplicationFrameHost as "other".
4) Linux: on X11, run `xprop -root -notype _NET_ACTIVE_WINDOW`, then `xprop -id <id> -notype WM_CLASS` (only WM_CLASS, never WM_NAME/_NET_WM_NAME). On Wayland (XDG_SESSION_TYPE=wayland):
   - GNOME works only if the user installs the "Focused Window D-Bus" extension: `gdbus call --session --dest org.gnome.Shell --object-path /org/gnome/shell/extensions/FocusedWindow --method org.gnome.shell.extensions.FocusedWindow.Get`. Use wm_class and drop the title. The built-in org.gnome.Shell.Eval is disabled outside unsafe mode.
   - Sway: `swaymsg -t get_tree`, take the node with focused=true and read its app_id.
   - KDE: a KWin script reading workspace.activeWindow.
   - Anything else: report "unsupported" and rely on manual status.
5) Do not depend on get-windows (9.3.0, MIT, node>=18.18). On Windows it is a native N-API addon installed through @mapbox/node-pre-gyp with a node-gyp fallback build. On macOS it runs a bundled universal Swift binary that by default prompts for Accessibility (only used for browser URLs) and Screen Recording (only used for window titles). It has no Wayland support. If it is ever used, call `activeWindow({accessibilityPermission:false, screenRecordingPermission:false})` and read only owner.name/bundleId.
6) Auth: per-user, per-device tokens created in Settings › Desktop helper.
   - Format `wcp_` + 32 random bytes in base64url, shown once.
   - Postgres `api_tokens` row: id, user_id, sha256(token), scope 'presence:write', label, created_at, last_used_at, revoked_at.
   - The helper keeps the token in ~/.config/workchop/helper.json (mode 0600), or in the macOS Keychain via the `security` CLI.
   - Endpoint `PUT /api/me/app-presence` with `Authorization: Bearer wcp_…`, body `{"app":"figma"|"vscode"|…|"other"|null,"platform":"macos"|"windows"|"linux","v":1}`, response 204.
   - Rate limit about 1 request per 2 s per token. Validate `app` against the shared allowlist plus "other". No CORS is needed.
7) Server: keep app presence in memory only (Tandem does the same: never persisted). Use a Map userId→{app, until} with a 45 s TTL. Add `app?: string|null` to PlayerState/PlayerPatch and broadcast through the existing `player:updated` event to every office room the user is in. Clear it on TTL expiry or when status is busy/focus. On Cloudflare the Worker already routes all /api traffic to the single container Durable Object, so in-memory state works there too.
8) Privacy defaults:
   - The feature is off until a helper is paired. The allowlist lives in shared/apps.ts as id → label, icon, and per-platform matchers (bundle ids, Windows ProcessName, Linux WM_CLASS).
   - Unknown apps are sent only as "other" and shown as "Working". The user can switch that to "hide".
   - Browsers and terminals map to "other" (no URLs, no titles). Users can deny individual apps, and there is a "pause sharing" toggle.
   - Manual status always wins: a picker with In Figma / In VS Code / In Slack / Heads-down / custom emoji+text, with an expiry of 30 min, 1 h or today.
   - The only in-browser signal worth adding is "Sharing screen/window/tab" from `track.getSettings().displaySurface`. Never use track.label.
PITFALLS:
 - Do not use `tell application "System Events"` on macOS. It sends Apple Events, which triggers an Automation (TCC) prompt attributed to the responsible process (Terminal, node or osascript). It also misidentifies Electron apps that share the process name 'Electron' (VS Code, Windsurf, Cursor). Use the NSWorkspace route through the JXA ObjC bridge and match on bundleIdentifier.
 - A long-running macOS process that polls NSWorkspace without running a run loop can return a stale frontmost app. Spawn a fresh osascript per poll, or pump NSRunLoop / observe NSWorkspace.didActivateApplicationNotification.
 - frontmostApplication can be nil (login, wake, screen saver), and the frontmost app may be loginwindow or ScreenSaverEngine when locked. Map those to null instead of crashing.
 - NSRunningApplication.localizedName is localized and not unique (VS Code reports 'Code'). Map on bundle id, not name.
 - Avoid Screen Recording and Accessibility permissions entirely. They are only needed for window titles and browser URLs, which we deliberately do not collect. get-windows asks for both BY DEFAULT unless {accessibilityPermission:false, screenRecordingPermission:false} is passed.
 - Windows: compiling Add-Type on every poll is slow (C# compile). Keep one long-lived PowerShell process and read its stdout. Spawn it with windowsHide:true, or a console window flashes.
 - Windows: GetForegroundWindow can return 0. Packaged/UWP apps report ApplicationFrameHost.exe. Elevated (admin) foreground processes may deny access to Path/MainModule from a non-elevated helper, so rely on ProcessName only.
 - Windows: under AppLocker/WDAC, PowerShell runs in ConstrainedLanguage mode, so Add-Type of Win32 APIs fails. Detect the language mode and report 'unsupported'. A Group Policy execution policy (MachinePolicy/UserPolicy) overrides -ExecutionPolicy; use -EncodedCommand inline commands rather than a .ps1 file.
 - Linux: xprop/xdotool are X11-only. Under a Wayland session they only see XWayland windows. Check XDG_SESSION_TYPE/WAYLAND_DISPLAY and choose the GNOME extension, Sway IPC or KWin route, or report unsupported.
 - Linux: never request WM_NAME/_NET_WM_NAME (titles). The GNOME Focused Window D-Bus extension returns 'title' too, so drop it before anything leaves the process.
 - getDisplayMedia track.label is not a usable app signal. Chrome returns 'window:<id>:<n>' and Firefox returns the full window title, which can leak document names. Use only getSettings().displaySurface.
 - Raw app names of non-allowlisted apps reveal personal activity (dating apps, job search, health). Map to allowlist ids ON THE DEVICE and send only {app: id|'other'|null}. Never log the raw name server-side.
 - Treat app presence as ephemeral. Hold it in memory with a TTL (around 45 s) and clear it when the helper stops; otherwise a crashed helper leaves a stale 'In Figma' badge. Do not persist it to Postgres. Hide it automatically when status is busy/away.
 - Tokens: store only a SHA-256 hash, scope it to presence:write, keep one per device, make it revocable, and show it once. Use a recognizable prefix (wcp_) so leaked tokens can be detected. Rate-limit the endpoint.
 - Tandem documentation could only be read through search-engine excerpts because tandem.chat and blog.tandem.chat are blocked by this sandbox's proxy. The pages date from the 2021–2022 era and Tandem's current behaviour may differ.
NON-CONFIRMED:

   -> The sandbox egress proxy blocks blog.tandem.chat and web.archive.org (403 on CONNECT), and a web search did not find the page. I could not confirm the quote or that it is still current. Treat "same route Tandem documents" and "Tandem never persists" (rec. item 7) as unconfirmed, low confidence. The design does not depend on them: NSWorkspace.frontmostApplication is confirmed independently by Apple docs (claim 4).

MISSED:
 - Node SEA in Node 22 (and 24) is CommonJS-only, so the 'ESM workchop-presence.mjs, package with SEA later' plan fails on Node 22. The v22.x and v24.x docs both say: "The single executable application feature currently only supports running a single embedded script using the [CommonJS] module system." The ESM entry ("mainFormat": "module") arrived in Node 25.7.0 (2026-02-24, PR #61813), and `--build-sea` in 25.5.0. Node 22 is maintenance LTS until 2027-04, Node 24 LTS until 2028-04, and Node 26 is Current. Either write the helper as .cjs or bundle it to CJS for Node 22/24 SEA, or build the SEA with Node 26. Sources: https://raw.githubusercontent.com/nodejs/node/v22.x/doc/api/single-executable-applications.md , https://raw.githubusercontent.com/nodejs/node/main/doc/changelogs/CHANGELOG_V25.md . Stability is still 1.1 in all branches.
 - Cloudflare deployment: helper heartbeats will keep the container awake 24/7 and will wake a stopped container. cloudflare/worker.ts sets IDLE_MS = 15 min of inactivity after "the last ordinary request" ("Realtime (WebSocket) traffic doesn't count"). A PUT every 15 s from any paired helper resets that timer forever and cold-starts a stopped container (up to 90 s of 503 'starting up'). The DB token lookup and last_used_at write on each call also keep Neon from suspending. Fix: in the Durable Object, answer /api/me/app-presence with 204 without starting the container when !ctx.container.running. Have the server tell the helper to back off (e.g. 204 plus Retry-After 300, or {active:false}) when the user has no live socket. Cache token hash to userId in memory and throttle last_used_at writes. Source: /home/user/workchop/cloudflare/worker.ts (IDLE_MS comment, start() and fetch()).
 - Windows loop bug: the snippet never checks $h. GetWindowThreadProcessId leaves the out variable unchanged on failure (sdk-api doc), so $p=0, and `Get-Process -Id 0` returns the 'Idle' pseudo-process (medium confidence, my own knowledge). The helper would then report 'Idle' instead of null. Add `if ($h -eq [IntPtr]::Zero) { [Console]::Out.WriteLine('') }`. Also map LockApp (Windows lock screen) and, on macOS, com.apple.loginwindow to null/away (low confidence, no primary source checked).
 - Windows deployment risk (low confidence, no primary source checked): `powershell -EncodedCommand` plus Add-Type DllImport of user32 GetForegroundWindow is a pattern that EDR/AMSI heuristics commonly flag in corporate fleets. Prefer passing the script on stdin (`-Command -`) over EncodedCommand. For corporate users, consider a small signed native helper. An unsigned SEA .exe also hits SmartScreen; the SEA docs show signtool signing for Windows and `codesign --sign -` (ad-hoc only) for macOS. Downloaded macOS binaries need Developer ID signing and notarization to pass Gatekeeper without warnings (https://developer.apple.com/tutorials/data/documentation/security/notarizing-macos-software-before-distribution.json).
 - GNOME 'Focused Window D-Bus' extension: the GitHub main branch metadata.json lists "shell-version": ["49", "50"], last commit 2026-04-16 'chore: support gnome 50'. GNOME Shell 51.0 was tagged 2026-09-14. On GNOME 51 distros (e.g. Fedora 45 / Ubuntu 26.10) the extension may be disabled until it is updated. extensions.gnome.org was blocked here, so this could not be confirmed. The extension's Get() also publishes the focused window's title (and pid) to any process on the session bus, which is a privacy cost Workchop asks users to accept. It now has a FocusChanged signal (`gdbus monitor --session --dest org.gnome.Shell --object-path /org/gnome/shell/extensions/FocusedWindow`), so polling isn't needed. gdbus prints GVariant text `('{...}',)`, so the JSON must be unescaped. Sources: https://raw.githubusercontent.com/flexagoon/focused-window-dbus/main/metadata.json , https://raw.githubusercont
 - Sway: app_id is "(Only windows) For an xdg-shell window, the name of the application, if set. Otherwise, null". XWayland windows (e.g. many Electron apps without Ozone/Wayland) have app_id null and need window_properties.class. Also walk floating_nodes, not only nodes. Sway's WINDOW event (0x80000003, change 'focus') allows `swaymsg -t subscribe '["window"]'` instead of polling get_tree. Source: https://raw.githubusercontent.com/swaywm/sway/master/sway/sway-ipc.7.scd
 - Cheap extra Wayland compositors instead of 'unsupported': Hyprland `hyprctl -j activewindow` ("gets the active window name and its properties"; read only `class`), from https://raw.githubusercontent.com/hyprwm/hyprland-wiki/main/content/configuring/core/advanced-configuration/using-hyprctl.md . niri `niri msg --json focused-window` (Request::FocusedWindow, Window.app_id), from https://raw.githubusercontent.com/YaLTeR/niri/main/niri-ipc/src/lib.rs
 - KDE is harder than implied. KWin scripting exposes Workspace.activeWindow and a windowActivated signal (src/scripting/workspace_wrapper.h), but a script can only push data out via callDBus(service, path, interface, method, ...) (src/scripting/scripting.cpp). Scripts must be loaded through org.kde.KWin /Scripting. A zero-dependency Node helper using only child_process cannot host a D-Bus service to receive those calls. It would need a workaround (dbus-monitor sniffing, or print() to the journal), so budget KDE as a separate effort or ship it later.
 - Repo fit: shared/types.ts Status is 'available' | 'busy' | 'away'; there is no 'focus' status, so 'clear when busy/focus' needs a new status or should read 'busy'. PlayerPatch/player:updated are keyed by socket player id, and server/realtime.ts emits to roomName(officeId). The presence service needs a userId to live player ids/rooms index, which depends on the accounts work. server/index.ts has a catch-all `app.use('/api', ...)` 404 that new routes must be registered before.
 - Token storage details (low confidence): `security add-generic-password -w <token>` puts the secret in argv, where other local users can see it via ps. Pipe it in or use the prompt form, or rely on the 0600 file. ~/.config is not the Windows convention; use %APPDATA%\Workchop\helper.json, protected by the user profile ACL (or DPAPI).
 - Rec. item 2 says the System Events route has an 'Electron' process-name bug. This is unsourced, and current VS Code builds rename the macOS executable to product.nameShort (build/lib/electron.ts: darwinExecutable: product.nameShort). Do not cite it as a reason; the Automation prompt alone is reason enough to avoid System Events.
```
